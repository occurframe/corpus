vectors:          184

## What this repository is

The versioned, language-neutral **authority** for Occurframe recurring-time
conformance. It contains the authored specification, Draft 2020-12 wire schemas,
authored registries, one JSON file per canonical vector, an independent Python
cron reference matcher, and the immutable Phase II RC1 evidence.

Occurframe is an executable conformance oracle, not a recurrence engine or
scheduler. Generated JSONL packs, observations, matrices and reports are derived
artifacts. **Incumbent behaviour never defines a normative expectation**: the
corpus records what a document says, what a policy axis is, or that a question is
genuinely ambiguous — never "what most libraries happen to do".

## What makes a vector

Each vector carries an input, the semantic context it must be read in, a
classification, the normative evidence behind it, an authored expectation, and a
rationale.

Classification and expectation mode are **independent**. Classification says why
a question has the answer it has — `NORMATIVE`, `POLICY_DEPENDENT`,
`DIALECT_DEPENDENT`, `AMBIGUOUS_STANDARD`, `KNOWN_DIVERGENCE` or `INVALID`.
Expectation mode says what shape the answer takes — `single`, `reject`,
`per_policy`, `per_dialect`, `admissible` or `open`.

That separation is deliberate. It lets the corpus say "several answers are
legitimate here, and which one is correct depends on this named axis" instead of
picking a winner and recording every other implementation as broken.

## Timezone-database provenance

A DST answer is reproducible only against a known timezone-database release, so
provenance is a first-class, mechanically distinct concept: an **exact** release,
a **bounded** range, or genuinely **unknown**. `unknown` is an honest answer and
is treated as such, not as a failure. The `tzdb.provenance` family makes the
requirement testable rather than assumed.

## Stability guarantees

- Vector IDs are permanent and never reused. Retired IDs remain in
  `registry/vector-ids.json` forever, with their successor recorded.
- Dialect IDs are permanent and versioned. A configuration variant that changes
  semantic claims gets its own ID. New entries may be added in a corpus minor
  version; renaming or removal requires a major version.
- Schema `$id` values are stable. An incompatible wire change requires a new
  schema identity and an appropriate corpus major version.
- The runner protocol versions independently of the corpus.
- Documentation/implementation disagreement is recorded with
  `evidence_grade: documentation_conflict`, not hidden.

A compatibility claim must name at least corpus version, dialect or RRULE
profile, semantic policy claims, tzdb provenance, engine identity and provenance,
and runtime. "Cron-compatible" is not a versioned identity.

## Verifying a distribution

The canonical digest is the SHA-256 over the canonical JSON serialisation of the
authored vectors, sorted by ID. It is derived from the vectors alone, so
repository metadata — a changelog, a licence, these notes — cannot change it.

```sh
cargo run -p xtask -- validate --corpus .
cargo run -p xtask -- verify-deterministic --corpus .
cargo run -p xtask -- pack --corpus . --output dist/occurframe-corpus-1.0.0-rc2
cargo run -p xtask -- verify-manifest --output dist/occurframe-corpus-1.0.0-rc2
```

A generated distribution carries `manifest.json` and `SHA256SUMS`; a consumer
verifies both, and Occurframe re-derives the canonical digest from the vectors it
actually loaded rather than trusting the manifest.

## Licensing

The authored semantic data — `vectors/`, `schemas/`, `registry/`, `spec/`,
`docs/` — is dedicated to the public domain under **CC0-1.0**, so that engine
maintainers can vendor vectors into their own test suites without friction.

The independent reference matcher in `reference/`, and its tests, are
**Apache-2.0**. The corpus *semantic data* is CC0; the reference *code* is not.

No blanket licence is asserted over `legacy/`: it mixes Occurframe-authored
research with material derived from third-party engines, and its per-directory
licensing remains an open question for the repository owner. See `LICENSING.md`.

## Known limitations

- This is a release candidate. Expectations may still be corrected with reviewed
  evidence before stable `1.0.0`.
- Some vectors carry an `open` expectation: the case is recorded and observations
  are preserved, but no expectation is authored yet. That is a stated gap in the
  corpus, not a gap in any engine.
- `legacy/` licensing is unresolved, as above.
- The corpus describes cron and RRULE semantics. It does not define, and must not
  be read as defining, scheduling execution behaviour.
